# Advanced Authoring Examples Implementation Design

## Summary

This design maps the cap4k public advanced examples for content publication back into
`cap4k-reference-content-studio` without replacing the current runnable happy path.

The implementation should extend the existing content publication / media processing
business line in two controlled ways:

- make value-object persistence visible through cap4k's preferred DB-first,
  separate-table shape;
- add a gated publication extension line that can demonstrate release readiness and
  Saga/process boundaries while keeping the current immediate publication path intact.

The goal is not to make the reference project more elaborate for its own sake. The goal is
to provide a standard, generator-friendly example that future cap4k generator work can
lift into templates and design vocabulary.

## Source Examples

This design consumes these cap4k public example pages:

- `cap4k/docs/public/authoring/examples/content-publication-value-object.zh-CN.md`
- `cap4k/docs/public/authoring/examples/content-publication-domain-service.zh-CN.md`
- `cap4k/docs/public/authoring/examples/content-publication-saga.zh-CN.md`

The examples all refer to the same content publication / media processing teaching domain.
The reference project should therefore remain in that domain and should not introduce a
new unrelated business scenario.

## Current Baseline

The current reference project already has the default path:

```text
CreateContentDraft
  -> SubmitContentForReview
  -> ApproveContentReview
  -> StartMediaProcessing
  -> callback / polling
  -> MarkMediaProcessingSucceeded
  -> MediaProcessingSucceededDomainEvent
  -> PublishContent
```

This path must remain the first learning path and the default `.http` happy path.

The project also already has:

- `PublicationEligibilityDomainService`;
- `PublishContentCmd`;
- callback ingestion through `ddd-integration-event-http`;
- polling fallback that feeds the same internal command surface;
- generated snapshot directories;
- flow analysis outputs.

The current gap is not that the happy path is broken. The gap is that the three advanced
concept examples are not yet represented in a standard, inspectable way.

## Goals

- Demonstrate cap4k value-object persistence using separate-table value objects.
- Keep value-object modeling compatible with DB-first generation and future design support.
- Improve publication eligibility from a boolean check into an auditable domain conclusion.
- Add a release-readiness extension line that is compatible with the current happy path.
- Preserve the default immediate publication path for existing readers and tests.
- Make the extension line visible through `.http`, tests, and analysis output.
- Avoid JSON-column value objects as the main teaching example.

## Non-Goals

- Do not turn the default happy path into a Saga.
- Do not enable Saga runtime just to satisfy the example page.
- Do not use JSON columns as the primary value-object demonstration.
- Do not claim that `value_object`, `domain_service`, or `integration_event` design tags are
  currently generated by cap4k design JSON.
- Do not introduce a frontend, authentication, production deployment, or a real media service.
- Do not make `ContentTitle` a separate table just to force a value-object example.

## Value Object Position

The reference project should treat value-object persistence in three tiers, but only the
third tier is the main implementation target for this slice.

| Shape | Meaning | Reference Project Position |
|---|---|---|
| inline column | a primitive field with value semantics | acceptable for simple values such as title, but not the main advanced example |
| JSON column | a serialized composite carrier | not the main cap4k generator-friendly path |
| separate table | DB-recognizable value object with `@VO` metadata | primary advanced example |

The reason is practical: cap4k can already recognize DB table annotations such as
`@ValueObject` / `@VO`, and the runtime has `ValueObject<ID>` plus JPA unit-of-work support
for value-object existence checks. JSON columns can be valid storage in business systems,
but they do not give the generator a clean first-class DB shape. They usually require a
handwritten JSON type, converter, or `@T` binding before the model becomes useful.

Therefore the reference project should demonstrate separate-table value objects first.

## Separate-Table Value Object

Add a value object under the existing `MediaProcessingTask` aggregate:

```text
MediaProcessingResultSnapshot
```

Recommended DB shape:

```sql
create table media_processing_result_snapshot (
    id varchar(64) primary key,
    media_processing_task_id uuid not null,
    external_task_id varchar(120) not null,
    result_status int not null,
    asset_sha256 varchar(64) not null,
    asset_location varchar(500) not null,
    completed_at timestamp not null,
    db_created_at timestamp not null,
    db_updated_at timestamp not null,
    constraint fk_media_processing_result_snapshot_task
      foreign key (media_processing_task_id) references media_processing_task(id)
);

comment on table media_processing_result_snapshot
  is 'Media processing result snapshot @Parent=media_processing_task;@VO;';
```

Column comments should keep the same DB custom annotation style used elsewhere in the
project. The `result_status` column should use enum metadata, for example:

```sql
comment '@T=MediaProcessingResultStatus;@E=0:SUCCEEDED:Succeeded|1:FAILED:Failed;'
```

The value object's identity must be deterministic. Its `hash()` should be based on stable
business value, not on incidental database timestamps. A practical first hash input is:

```text
mediaProcessingTaskId + externalTaskId + resultStatus + assetSha256 + assetLocation
```

This table is owned by `MediaProcessingTask`; it is not a new aggregate root and should not
have independent lifecycle commands.

## Generator-Readiness Constraint

The first implementation may need handwritten or override code because cap4k's current
generator surface does not yet fully produce every piece of value-object runtime code from
DB metadata. That must be handled explicitly:

- DB schema must carry `@VO` metadata in the standard form.
- Handwritten code must use names and package positions that a future generator can produce.
- Do not invent project-local annotations or naming conventions.
- Do not hide unsupported generator behavior behind local helper magic.
- Generated snapshots should be refreshed if generation output changes.

The intended future generator contract should be inferable from the project:

```json
{
  "tag": "value_object",
  "name": "MediaProcessingResultSnapshot",
  "aggregate": "MediaProcessingTask",
  "persistence": "separate_table",
  "owner": "MediaProcessingTask",
  "identity": "hash"
}
```

This JSON is illustrative only. It is not current supported `design/design.json` input.

## Domain Service Position

`PublicationEligibilityDomainService` should remain a domain service, but it should not
return only `Boolean`.

It should return a small domain conclusion that can be audited and tested:

```text
Eligible
ContentNotApproved
MediaProcessingNotSucceeded
TaskDoesNotBelongToContent
ReleaseReadinessNotSatisfied
```

The service still must not:

- call repositories;
- send commands;
- publish events;
- save unit of work;
- drive callback, polling, or release-readiness flow.

Application handlers load aggregates, call the service, interpret the conclusion, invoke
aggregate behavior, and call `Mediator.uow.save()`.

## Release Policy Split

Add a publication policy to `Content`:

```text
ReleasePolicy = IMMEDIATE | GATED
```

Default behavior remains:

```text
releasePolicy = IMMEDIATE
```

The existing path remains valid:

```text
MediaProcessingSucceededDomainEvent
  -> PublishContentCmd
```

The new gated extension path should only apply when the content was created for gated
publication:

```text
MediaProcessingSucceededDomainEvent
  -> if Content.releasePolicy == IMMEDIATE:
       PublishContentCmd
  -> if Content.releasePolicy == GATED:
       OpenPublicationReleaseReadinessCmd
```

This split preserves the current happy path and gives the advanced Saga example a real,
bounded extension point.

## Release Readiness Extension

Introduce a process-state aggregate:

```text
PublicationReleaseReadiness
```

It records cross-time publication readiness for gated content:

```text
id
contentId
mediaProcessingTaskId
state = WAITING | READY | CANCELLED | EXPIRED
copyrightStatus = WAITING | PASSED | REJECTED
manualConfirmationStatus = WAITING | CONFIRMED
releaseWindowOpensAt
releaseWindowClosesAt
readyAt
cancelReason
dbCreatedAt
dbUpdatedAt
```

This is not a value object. It changes over time and represents a process state.

The first extension should support a narrow flow:

```text
OpenPublicationReleaseReadinessCmd
  -> creates WAITING readiness for gated content

PassCopyrightReviewCmd
  -> marks copyright status passed

ConfirmManualReleaseCmd
  -> marks manual confirmation confirmed

CompletePublicationReleaseReadinessCmd
  -> checks release window + copyright + manual confirmation
  -> marks readiness READY
  -> sends PublishContentCmd
```

The release window may be satisfied synchronously by command input in the first slice. A
timer or scheduler is not required unless the implementation explicitly chooses to add one.

## Saga Boundary

The gated extension is a Saga/process candidate because it waits for future facts:

- copyright review result;
- release window;
- manual confirmation.

However, the first implementation should not enable or depend on full cap4k Saga runtime
unless there is a separate design decision to teach that runtime surface. The safer first
shape is a normal process-state aggregate plus commands/subscribers. This keeps the example
valid and generator-friendly while leaving a clear migration point for future Saga support.

Documentation should say:

- the default path still does not need Saga;
- the gated line demonstrates why Saga/process thinking becomes relevant;
- `PublicationReleaseReadiness` is the explicit waiting/recovery state;
- future Saga runtime support can replace or wrap this process shape.

## Integration With Callback And Polling

Callback remains the main external input path. Polling remains fallback.

Both paths should converge before updating domain state:

```text
callback payload / polling observation
  -> MediaProcessingResultSnapshot input
  -> MarkMediaProcessingSucceededCmd
  -> MediaProcessingTask.markSucceeded(snapshot)
  -> MediaProcessingSucceededDomainEvent
```

This keeps the existing rule: callback and polling do not become two separate business
truth paths.

The command should not receive arbitrary external DTOs. It should receive either:

- fields that map directly to `MediaProcessingResultSnapshot`; or
- a small request payload whose shape is intentionally equivalent to the value object.

The implementation should prefer the shape that is closest to future generation.

## HTTP Surface

The current `.http` happy path should stay first:

- `http/content.http`
- `http/review.http`
- `http/query.http`
- `http/media-processing.http`

Add a separate advanced path:

```text
http/advanced-release-readiness.http
```

That file should create or mark content as gated and then drive:

```text
media success
open readiness
pass copyright review
confirm manual release
complete readiness
query content published
```

If the implementation adds HTTP endpoints, they should live in adapter controllers and send
commands through `Mediator.cmd`. They should not call repositories or domain services directly.

## Tests

Required test surface:

- domain behavior tests for `MediaProcessingResultSnapshot` hash and value semantics;
- domain behavior tests for `PublicationReleaseReadiness` state transitions;
- domain service tests for structured publication eligibility conclusions;
- application tests for immediate-vs-gated split after media success;
- smoke test or `.http`-equivalent test for the advanced gated path if runtime surface is added.

Tests should remain teaching tests. Do not add architecture-policing tests whose purpose is
only to guard previous implementation mistakes.

## Analysis Output

After implementation, analysis should make both paths visible:

- immediate media-succeeded-to-publish path;
- gated media-succeeded-to-readiness-to-publish path.

If generated or hand-written flow artifacts are committed, README should explain that they
are evidence/inspection outputs, not the primary manual operation surface.

## Documentation Updates

Update README files to include a short advanced examples mapping:

- Value Object: `MediaProcessingResultSnapshot` as separate-table VO.
- Domain Service: publication eligibility returns auditable conclusion.
- Saga: default path still does not need Saga; gated release readiness is the extension
  where Saga/process boundaries become relevant.

Do not make README's first-run section depend on the advanced path.

## Compatibility Rules

- Existing immediate happy path behavior must remain runnable.
- Existing `.http` order must remain valid.
- New advanced path must be opt-in.
- `Content` remains the only aggregate that ultimately enters published state.
- `MediaProcessingTask` remains responsible for media task lifecycle and result snapshot ownership.
- `PublicationReleaseReadiness` owns waiting state only; it does not publish content by direct mutation.
- Publishing still goes through `PublishContentCmd`.

## Open Implementation Choices

The implementation plan should decide these details explicitly:

- whether gated content is created through a separate command or an optional field on
  `CreateContentDraftCmd`;
- whether release-window satisfaction is checked by `CompletePublicationReleaseReadinessCmd`
  only, or also by a lightweight job;
- how much of `MediaProcessingResultSnapshot` is generated from DB metadata and how much must
  remain handwritten until value-object generation improves;
- whether generated snapshots should include value-object output in this slice.

The recommended defaults are:

- use a separate advanced command or endpoint for gated content, to keep the first learning
  path clean;
- check release-window satisfaction inside the complete command in the first slice;
- keep handwritten code standard and obvious where generator support is incomplete;
- refresh snapshots only after confirming the generator output is meaningful and compiles.
